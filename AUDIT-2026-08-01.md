### D.2 Architecture

- **Framework/libraries:** **None.** 100% vanilla HTML/CSS/JS, no build step, no dependencies, **no CDN** — every asset is local and same-origin. This satisfies the "no server / no backend / offline / iPad-Safari" constraints: there is not a single network call to any backend.
- **Module structure:** two independent pages sharing one CSS file and one service worker. `app.js` drives the customer page; `manager/manager.js` drives the manager page. They share **no JS module** — constants (DB name, CSV/ZIP helpers, service/add-on lists) are **duplicated** in both files. They communicate only through (a) the shared IndexedDB database and (b) a `BroadcastChannel('tb_updates')` ping so the manager auto-refreshes when the waiver page edits a record.
- **Routing between customer and `/manager/`:** plain page navigation, no router. Customer → manager via the **Manager Access** button (`window.location.href = './manager/'`) or by typing the URL. Manager → customer via the **Waiver** tab (`window.location.href = '../'`). Within manager, "tabs" (History/Sales) toggle `.hidden` on `#viewHistory`/`#viewSales`; the PIN gate toggles `#pinCard`/`#mgrCard`.
- **Full flow (launch → completed waiver):**
  1. Launch `index.html` (installed to Home Screen, `display: standalone`). SW registers; assets served from cache (offline-capable).
  2. Client fills Name, Date (defaults to today), Contact (required), Address, Service, Add-Ons (modal), Therapist, Time Start, and any medical conditions; "Other" requires text if checked.
  3. Client ticks the **Privacy Notice consent**. Only then does **Take a Photo** enable (when photo capture is enabled).
  4. **Take a Photo** opens the iOS native camera via `<input type="file" accept="image/*" capture="user">`. On capture, consent is locked, a preview shows, `photoTaken = true`, and the **signature canvas enables**.
  5. Client signs on the canvas.
  6. `validate()` enables **Submit** only when name, date, contact, service, therapist, time-start, consent, photo (if required) and a non-empty signature are all present.
  7. **Submit** writes one record to IndexedDB (`submissions`), pings the manager via BroadcastChannel, shows "Submission successful", resets the form, and re-arms the photo/signature gate for the next client.
  8. Manager opens `/manager/`, enters the manager PIN, and reviews **History** (all fields + per-record photo/signature) or **Sales** (priced totals, filters, chart), and exports.

### D.3 Data model

- **Storage API:** **IndexedDB** for waiver records; **localStorage** for settings/prices/sales-archive. (Photos & signatures live in IndexedDB, not localStorage.)
- **IndexedDB:** database **`thai_boran_waiver_db`**, **version `1`**, one object store **`submissions`**, **`keyPath: 'id'`**, **no indexes** (`createIndex` appears nowhere). Created identically in both `app.js` and `manager/manager.js`.
- **Record schema** (`submissions`):

  | Field | Type | Notes |
  |---|---|---|
  | `id` | string | `crypto.randomUUID()` (fallback time+random). Primary key. |
  | `createdAt` | number | `Date.now()` epoch ms (UTC). Used for sorting. |
  | `timestamp` | string | `"YYYY-MM-DD HH:MM:SS"` in **device-local** time. |
  | `name`,`date`,`address`,`contact`,`services`,`therapist`,`addons`,`timestart` | string | Form fields. `date` is local `YYYY-MM-DD`. `addons` = `"A; B; C"` or `"None"`. |
  | `conditions` | string | Concatenated medical conditions, `"…; …;"`. |
  | `sigFile` | string | `"<sanitizedName>.png"`. |
  | `photoFile` | string | `"<sanitizedName>.jpg"` (empty if photo capture was disabled for that client). |
  | `sigBytes` | **Array&lt;number&gt;** | Signature PNG bytes as a plain JS number array (`Array.from(Uint8Array)`). |
  | `photoBytes` | **Array&lt;number&gt;** | Photo JPEG bytes as a plain JS number array. |

- **Photo encoding & size:** the working capture path is the **native file picker**, which stores the camera's JPEG **as-is — no downscaling or re-compression** (`state.photoBlob = f`). On a modern iPad that is typically **~2–4 MB per photo**, serialized into IndexedDB as an `Array<number>` (one JS array element per byte — an inefficient encoding; a `Blob`/`ArrayBuffer` would be far lighter). *(A second, live-`getUserMedia` modal exists and would JPEG-compress at 0.92, but it is effectively dead code — the button uses the native picker.)*
- **Signature encoding & size:** `canvas.toBlob('image/png', 1.0)` of the 220px-tall, DPR-scaled canvas → mostly-white PNG, roughly **~15–60 KB**, stored the same `Array<number>` way.
- **Approx. total per record:** **~2–4 MB**, dominated by the photo.
- **"Nothing uses localStorage"? — FALSE.** localStorage stores four keys (not the waiver records, but important state):
  - `tb_photo_capture_enabled` — receptionist photo on/off toggle.
  - `tb_price_sets_v1` — the **manager-editable price list** (array of `{effectiveFrom, services{}, addons{}}`).
  - `tb_price_locked_v1` — price edit lock flag.
  - `thai_boran_sales_archive_v1` — a **frozen sales snapshot** written before "Clear Saved Data", so historical revenue survives a records wipe.
  > Consequence: prices and archived sales are **not** in IndexedDB and are **not** included in any export. They live only in Safari's localStorage and are lost if site data is cleared. Also, since totals depend on `tb_price_sets_v1`, moving the DB without the prices yields different numbers.

### D.6 PWA / iOS specifics

- **Manifest:** valid; `display: standalone`, `start_url ./index.html`, 192/512 icons, white theme. No `orientation` lock.
- **Service worker (`sw.js`):** precaches all 12 assets on `install` (`cache.addAll`), `skipWaiting()`, deletes non-current caches on `activate`, `clients.claim()`. ### D.8 Bug hunt

Severity: **Critical** = data loss / broken update path / security exposure; **Major** = fails in common cases; **Minor** = quality/edge.

**#1 — Service worker serves stale code after every update unless `CACHE_NAME` is bumped — Critical.**
`sw.js` is cache-first over precached app files. After you deploy new `app.js`/`manager.js`/`index.html`, installed iPads keep serving the **old** cached versions until `CACHE_NAME` (`'thai-boran-waiver-v2'`) is changed to force `activate` to drop the old cache. The name is a manual string with no content hash. For an app that received 22 rapid edits, this is a live trap: forget to bump it and the fix never reaches the iPad. *Failure mode:* deployed fixes silently don't appear.

**#2 — `app.js` throws on every customer-page load (references buttons that don't exist) — Major.**
`app.js:1177` runs `el('btnExport').addEventListener(...)` and `:1179` `el('btnClearAll').addEventListener(...)`, **unguarded**, but neither `btnExport` nor `btnClearAll` exists in `index.html` (export/clear were moved to the manager page). `el()` returns `null` → `null.addEventListener` throws a `TypeError` inside `setupEvents()`, which propagates out of the un-`catch`ed async `init()`. Everything wired *before* line 1177 works (validation, photo, signature, submit), but everything *after* silently never runs: the **iPad edge-swipe-navigation guard is never installed**, the offline hint never initializes, and **the Date field is not defaulted to today**. *Failure mode:* an accidental edge-swipe can navigate away and lose an in-progress waiver; console shows an uncaught error on every load. (Guard these with `if (el('btnExport'))` like the other optional buttons, or remove the dead lines.)

**#3 — No working bulk export of photos+signatures; `exportZipAll` is dead code — Critical (backup).**
The manager wires only **Export CSV** (`exportCsvOnly` — text fields only, **no images**) and per-record **Export This Record (ZIP)**. The full-data `exportZipAll()` (CSV + all photos + all signatures) is **defined but attached to no button**. On the customer page, `exportAll()` is wired to the non-existent `btnExport` (Bug #2), so it never runs either. *Failure mode:* the only way to get photos/signatures off the iPad in bulk is to open each record and export it individually — there is no one-tap complete backup. See Step E.

**#4 — Photos stored full-resolution as `Array<number>` → IndexedDB bloat & quota risk — Critical.**
The native picker stores the raw camera JPEG (~2–4 MB) with no downscale/recompress, serialized as a per-byte JS number array. At ~3 MB/record, storage climbs fast (200 records ≈ 600 MB). iOS Safari can **evict** origin storage under pressure and enforces quotas; a standalone PWA is more durable than a tab but not guaranteed. *Failure mode:* quota exhaustion / eviction in the low-hundreds of records, with no automatic backup. Mitigation would be to downscale to ~1000px and store a `Blob`.

**#5 — No proactive IndexedDB quota handling; recovery path is destructive — Major.**
`submit()` wraps `dbPut` in try/catch and `alert()`s the error, so a `QuotaExceededError` is at least *surfaced* (and the form isn't cleared, so the client can't sign and vanish). But there is no graceful degradation, no "storage almost full" warning, and the only way to free space is **Clear Saved Data**, which destroys everything. *Failure mode:* once full, staff must wipe all data (after manually exporting) to continue.

**#6 — Whole-dataset ZIP/CSV is built entirely in memory (won't scale) — Major.**
`exportZipAll`/`exportAll` concatenate every photo into one `Uint8Array` in memory; the ZIP builder uses 32-bit (`u32`) sizes/offsets (no ZIP64). With hundreds of multi-MB photos this exhausts the tab's memory (crash) and breaks past 4 GB total. *Failure mode:* export crashes exactly when the dataset is large enough to most need backing up. (Also relevant only once Bug #3 is fixed to expose a bulk export.)

**#7 — Duplicate client names collide inside exports — Major.**
`sigFile`/`photoFile` are derived from the name (`"<sanitizedName>.png/.jpg"`). IndexedDB keeps same-named clients separate (unique `id`), but every export writes them to the **same** archive path (`photos/JohnSmith.jpg`) and the same CSV filename, so the second overwrites the first **in the export**. *Failure mode:* backups silently lose photos/signatures for any repeated name.

**#8 — Signature is wiped on orientation change / resize — Major.**
`setupSignature().resize()` is bound to `window 'resize'` and **clears the canvas** (fills white, `sigDirty=false`) every time it fires. Rotating the iPad mid-signature erases the signature. DPR mapping itself is correct (setting `canvas.width` resets the transform, then `scale(dpr)`), so there's no coordinate drift — only the wipe. *Failure mode:* client signs, rotates, signature gone; must re-sign.

**#9 — Non-ASCII-only names are blocked from submitting — Major (locale).**
`sanitizeNameForFile` strips everything except `[A-Za-z0-9_-]`. A name written only in Thai/Chinese/other non-Latin script → empty `safeName` → `submit()` alerts *"Name contains no valid characters for filenames"* and refuses. *Failure mode:* legitimate clients whose names aren't Latin cannot complete the waiver.

**#10 — Unhandled promise rejections — Minor.**
`init()` (both pages) is async and called without `.catch`; combined with Bug #2 the customer page logs an uncaught rejection every load. `navigator.serviceWorker.register('./sw.js')` has no `.catch`. `unlockIfPinOk` calls `loadRows()` without awaiting/catching. None crash the page outright, but errors are swallowed/noisy.

**#11 — Camera denial/cancel gives no feedback — Minor.**
With the native picker, cancelling or denying the camera fires `change` with no file → `if(!f) return;` — silent. No crash, but also no "photo required" nudge. (The unused `getUserMedia` path does `alert()` on failure.)

**#12 — Timezone (Philippines UTC+8) — Minor, mostly OK.**
Dates/timestamps use **device-local** time, and sales filters compare the stored local `date` strings, so day/month/year filtering is correct **as long as the iPad clock is set to PH time**. One inconsistency: the manager Edit-Records list and the sales chart derive display strings from `createdAt` via `toISOString()` (**UTC**), so those show ~8 h behind the local `timestamp` used elsewhere. Cosmetic, but can misattribute a late-night record to the previous day in those two spots.

**#13 — Sales chart vs table can disagree after a price change — Minor.**
The table uses `calcSalesForAnyRow` (respects each archived row's frozen total), but `renderMonthlyChartFromAllRows` uses `calcSalesForRecord` (recomputes with *current* prices). After editing prices and archiving, the chart and the table can show different numbers for the same period.

**#14 — Validation gaps — Minor.**
`contact` (`type=tel`) accepts any characters; prices accept decimals despite `step=1` (`Number("150.5")` → 150.5), so totals can show fractional pesos; no field length caps. Low risk.

**#15 — Data loss on refresh mid-flow — Major (inherent).**
All in-progress state (photo blob, signature, field values) is in memory only. A reload/crash/edge-swipe before Submit loses the whole in-progress waiver; there is no draft persistence. Combined with Bug #2 (edge-swipe guard disabled) and Bug #8 (rotate wipes signature), mid-flow loss is more likely than it should be on a public kiosk.

### D.9 Backup / export (can data leave the iPad?)

- **Bulk export of everything (records + photos + signatures): NOT currently possible via the UI.** The full-export function `exportZipAll` exists but is wired to no button (Bug #3). The customer-page `exportAll` is wired to a non-existent button (Bug #2).
- **What *does* work today:**
  - Manager → **Export CSV**: all records' **text fields only** — **no photos, no signatures**.
  - Record detail → **Export This Record (ZIP)**: one record's CSV + its photo + its signature — **one record at a time**.
- **Not exported at all:** the **price list** (`tb_price_sets_v1`) and the **archived sales snapshot** (`thai_boran_sales_archive_v1`) live only in localStorage and are in no export path.
- **Bottom line:** there is **no one-action, complete backup** of the iPad's data. Photos and signatures can only be extracted record-by-record. If the iPad is lost, reset, or its site data cleared, everything not manually exported (and all prices/sales-archive regardless) is gone. **Flagged as a priority gap.**
